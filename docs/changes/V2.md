## Known issues
Bugs found during V2 that are not part of any change. Each gets its own change ID when it is scheduled.

**First swing after a restart: animation lags the beats (pre-existing).** Found in review of V2-03 (November 2026).
- Steps: press play, then change the Background loop (or, since V2-03, Weight shift) while playing.
- Actual: on the first swing after the restart only, the scale's lights and sweep run a little behind the sound (takeaway, top, impact). From the second swing they line up.
- Expected: lights match the beats from the first swing after a restart.
- Pre-existing: confirmed by the developer on the live app (`main`) with the Background loop switch, so it is not caused by V2.
- Suspected cause (not confirmed): the first swing of every run uses a fixed fallback output delay (`resolveOutputDelayForSwing` in `src/ui/lib/outputDelay.ts`: iOS 3 ms, Android 280 ms, desktop 50 ms). Later swings use the browser's reported value. A render hiccup right after the restart is another candidate.
- Cause (confirmed with a Pixel 10 Audio lab log, November 2026): the first swing logged `280 ms (fallback)` and every later swing `56 ms (reported)`, so the first swing's lights were about 224 ms late. Fix: V2-13 (restarts fixed). **Still open (small, accepted for now):** the very first Play after the page loads still times its first swing with the platform guess, because the browser reports 0 ms at that moment (Pixel 10 log: `280 ms (fallback) first swing, browser said 0 ms`, then 56 ms reported), so those lights are about 224 ms late, once per page load. Ideas to refine later in the real app: save the last reported delay on the device and start from it next visit (needs a decision, because `tech.md` says only the theme is stored), or wait for the browser to report a value before the first run (changes audio scheduling, not advised). Mac first-Play log not yet collected.
